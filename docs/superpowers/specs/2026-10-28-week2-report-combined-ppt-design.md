| --- | --- | --- |

## 第二部分：双人模块深讲 PPT 设计稿 v1.2

### 智能学习规划助手双人模块深讲 PPT 设计稿

> 文档版本：v1.2
>
> 日期：2026-10-28
>
> 建议页数：8 页
>
> 建议时长：12 至 14 分钟
>
> 结构：A 四页，B 四页
>
> 项目状态：模块设计已定义；代码、原型和测试证据待核验

#### 1. 精简原则

本稿只保留两人的模块深讲，不重复项目背景、痛点、总体计划和完整技术架构。

每人的四页固定采用相同结构：

1. 模块功能清单。
2. 核心业务流程。
3. 技术实现。
4. 项目亮点与验收证据。

所有功能按“用户动作 -> 系统结果 -> 技术支撑 -> 验收方式”表达。没有实际证据时写“待核验”，不把设计写成已完成实现。

#### 2. 第 1 页：A 的模块与功能清单

**页面标题：** A 负责从学习目标到可校验的首次计划

**页面结论：** A 的核心任务是把资源、目标、诊断、证据和路径连接成一条可信规划链。

| 模块 | 具体功能 | 用户可见结果 |
| --- | --- | --- |
| 资源与知识底座 | 教师上传 Markdown/TXT/PDF、解析切分、建立索引、发布/下架、学生阅读、阅读时长与完成记录 | 有权限学生能阅读资源，学习记录可查询 |
| 目标与诊断 | 创建/修改/归档目标、解析 `GoalSpec`、生成 6 至 12 道诊断、初始化掌握度 | 学生看到结构化目标和诊断结果 |
| 搜索与可信引用 | 本地数据库/RAG 优先、覆盖检查、缺口触发千问联网搜索、来源和时效校验 | 正式路径中的知识点有真实来源 |
| 图谱与路径 | 先修 DAG、知识缺口、拓扑排序、全局预算排期、候选路径、规则审查、任务拆解 | 学生看到无先修冲突且可执行的学习路径 |
| 规划支撑 | 四智能体编排、教师任务负荷接口、画像事实输入、路径版本、解释和运行轨迹 | 路径可以解释、复查和接受 |

**关键边界：**

- LLM 生成候选内容，图谱和确定性规则决定路径是否可行。
- 缺失证据或来源无法核实时只能进入 `draft`。
- 教师任务不由 A 直接写入路径，只通过负荷接口参与重排建议。
- A 向画像提供目标、诊断、掌握度、证据、路径进度和任务负荷等事实，不负责最终学生画像和班级画像聚合。

**版式：** 五行模块表，右侧用一条从上到下的链路标出“资源 -> 目标 -> 诊断 -> 路径 -> 审查”。

**建议时长：** 约 75 秒。

#### 3. 第 2 页：A 的核心流程

**页面标题：** 首次学习计划由候选生成、覆盖检查和规则审查共同完成

**主流程：**

```text
教师发布授权资源
→ 学生输入目标与时间预算
→ GoalDiagnosisAgent 解析目标并生成诊断
→ A 写入诊断、证据和路径事实，供 B 刷新学生画像
→ 知识覆盖检查：本地资源、题库、图谱、RAG
→ 本地有缺口或声明具有时效性时按需联网
→ PathBuildingAgent 生成候选路径
→ PlanReviewAgent 校验先修、预算、负荷、引用和重复节点
→ 审核通过后展示路径、解释和任务
→ 学生接受路径
```

**三类关键处理：**

| 情况 | 系统行为 |
| --- | --- |
| 本地资料完整 | 不调用联网搜索，直接进入路径生成和审查 |
| 本地存在可检索缺口 | 使用千问原生搜索补齐，合并后重新检查，最多两轮 |
| 证据不足或来源不可验证 | 降级为 `draft`；不可发布正式路径 |

**输入与输出：**

- 输入：目标、当前基础、时间预算、诊断答案、授权资源、本地 RAG、按需 Web 证据。
- 输出：路径版本、任务排期、引用、规则结果、路径解释、运行轨迹和画像事实事件。

**画像联动：**

- 学生画像中的掌握状态、薄弱点和证据覆盖使用 A 产出的诊断、证据和 BKT 快照。
- 路径变化和教师任务负荷变化写入领域事件，供 B 判断画像是否过期。
- A 不根据模型回答直接写入画像数值。

**版式：** 主流程横向排列，下面单独画“三路分支”。右侧增加一个最短输入输出框，避免页面全是流程节点。

**讲述重点：** 先讲一次“本地完整不搜索”的正常路径，再讲“有缺口才联网”的异常路径。

**建议时长：** 约 90 秒。

#### 4. 第 3 页：A 的技术实现

**页面标题：** A 的技术核心是受控 Agent 编排与确定性校验

| 技术层 | 具体技术 | 解决的问题 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite、React Flow、TanStack Query | 路径图、诊断、任务和运行状态展示 |
| API | FastAPI、Pydantic、OpenAPI、REST | 请求校验、统一接口和异步运行状态 |
| Agent | LangGraph Coordinator、GoalDiagnosisAgent、PathBuildingAgent、PlanReviewAgent | 有状态路由、结构化交接、画像事实输入和有限重试 |
| 云端模型 | 阿里云百炼/DashScope 千问 API，默认候选 `qwen-plus` | 目标理解、内容生成、查询和解释 |
| 本地证据 | SQLite FTS5、Chroma 向量索引、混合检索 | 课程专属资料检索和真实引用 |
| 知识结构 | 知识图谱、先修边、DAG、拓扑排序 | 先修关系、知识缺口和路径顺序 |
| 规则层 | JSON Schema、Coverage Checker、Citation Validator、Constraint Validator | 格式、覆盖、引用、学时和负荷校验 |
| 数据与测试 | SQLite 版本记录、Agent 轨迹、pytest、Playwright | 可追溯、幂等、回归和端到端验证 |

**共享数据对象：**

- `GoalSpec`
- `LearningPath`
- `PathItem`
- `Evidence`
- `ValidationResult`
- `ReplanRequest`
- `LearnerSnapshot`
- `ProfileFactEvent`

**边界：**

- API Key 只在服务端使用。
- LLM 不直接写业务表，也不拥有最终可行性判定权。
- 正式路径必须有覆盖检查、引用和规则校验记录。
- 画像数值由 B 的确定性聚合服务计算，A 只提供可核查事实。

**版式：** 四层架构图：React -> FastAPI -> Agent 与本地服务 -> SQLite/Chroma/DashScope；右侧只列共享对象和三个边界。

**建议时长：** 约 75 秒。

#### 5. 第 4 页：A 的项目亮点与验收证据

**页面标题：** A 的亮点是让生成内容可查、可验、可拒绝

**项目设计亮点：**

| 亮点 | 常规做法 | 本项目做法 |
| --- | --- | --- |
| 本地优先的覆盖门控 | 每次都调用模型或搜索 | 先检查本地资源、题库、图谱和 RAG；完整时不联网 |
| 生成与验证分离 | 让模型直接生成并发布计划 | Agent 生成候选，图谱和确定性规则审查最终路径 |
| 声明级可信证据 | 只检查是否存在 URL | 保存来源域名、时间、哈希、支持片段和新鲜度 |
| 权限感知知识检索 | 登录后检索全部资料 | RAG、引用下载、轨迹和云端发送分别检查权限 |
| 画像事实输入 | 画像由模型自由总结 | A 提供诊断、掌握度、证据和任务进度事实，B 确定性聚合 |

**验收示例：**

1. 本地材料完整时，运行轨迹中没有联网搜索调用。
2. 查询最新版本资料时，路径包含本次搜索来源和抓取时间。
3. 人为制造先修冲突时，`PlanReviewAgent` 返回规则错误并阻止发布。
4. 外班教师或学生无法通过资源链接访问未授权内容。
5. 诊断或任务进度变化后产生画像事实事件，B 能据此生成新的学生画像版本。

**证据记录：**

`版本 -> 输入 -> 运行 ID -> 规则结果 -> 引用 -> 实际结果 -> 结论`

**版式：** 左侧五行亮点对照，右侧五条验收示例；底部只保留证据记录格式。

**表述边界：** 使用“项目设计亮点”，不写“行业首创”。

**建议时长：** 约 90 秒。

#### 6. 第 5 页：B 的模块与功能清单

**页面标题：** B 负责账号、班级、任务、反馈和重规划平台链

**页面结论：** B 的核心任务是让教师能发布和查看，学生能学习和提交，并把行为、任务和掌握事实汇聚成可刷新画像。

| 模块 | 具体功能 | 用户可见结果 |
| --- | --- | --- |
| 账号与权限 | 管理员、教师、学生登录/退出、账号停用、RBAC、班级和对象级授权 | 每个角色只能访问自己的业务数据 |
| 班级与任务 | 建班、邀请码、成员、全班/指定学生任务、撤回、提交和逾期补交 | 教师管理本人班级，学生完成本人任务 |
| 练习反馈 | 客观题评分、答案、解析；主观题待复核；评分版本保存 | 学生获得可追溯反馈 |
| BKT 与重规划 | 掌握度快照、阈值判断、补强任务、局部/全局重规划 | 低掌握度触发调整建议，学生接受后生效 |
| 学生画像 | 学习上下文、行为、掌握状态、证据质量、风险、数据完整度、版本与历史 | 学生看到本人完整画像；教师只看本班授权投影 |
| 班级画像 | 参与度、任务指标、学习时长、掌握分布、共性薄弱点、风险学生、数据质量 | 教师看到本班聚合画像和刷新时间 |
| 画像刷新 | 事件水位、`stale` 检测、版本化快照、刷新历史、失败回退 | 事件变化后画像更新，不把旧快照冒充最新 |
| 进度与审计 | 联合预算、进度统计、权限审计、画像访问审计 | 教师看到可核查的进度和审计记录 |

**关键边界：**

- 教师任务不直接写入 AI 路径。
- 前端隐藏菜单不能代替服务端权限检查。
- 待复核主观题不更新 BKT。
- 班级画像只聚合本班授权投影，不包含私人目标、其他班证据或隐藏备注。
- 无分母时显示“暂无数据”，不以 0% 或 0 分钟冒充真实观测。

**学生画像六类字段：**

`learning_context`、`learning_behavior`、`mastery_state`、`evidence_quality`、`risk_summary`、`data_quality`

**班级画像八类字段：**

`class_scope`、`participation`、`task_metrics`、`learning_time`、`mastery_distribution`、`common_weak_nodes`、`risk_students` 与 `data_quality`

**版式：** 模块表放在上半页，底部用两条横向字段带分别列出“学生画像六类字段”和“班级画像八类字段”；避免把画像只写成一个普通统计页面。

**建议时长：** 约 90 秒。

#### 7. 第 6 页：B 的核心流程

**页面标题：** 学习事件驱动画像刷新，再支撑教师查看和重规划

**平台任务主流程：**

```text
管理员创建账号
→ 教师创建班级并生成邀请码
→ 学生加入班级
→ 教师向全班或指定学生发布任务
→ 学生阅读、提交任务或完成练习
→ 系统保存提交和评分反馈
→ 客观题结果生成证据并更新 BKT
→ 低掌握度或负荷冲突生成重规划建议
→ 学生接受或拒绝调整
→ 教师查看最新班级和学生进度
```

**画像刷新闭环：**

```text
诊断提交 / 打卡 / 教师任务提交 / 资源阅读 / 评分 / BKT / 班级成员变化
→ 写入领域事件
→ 比较 source_watermark
→ 水位未变：返回当前快照
→ 水位变化：生成新的学生画像和班级画像版本
→ 旧版本只读，失败保留上一有效版本并标记 stale
```

**两类关键处理：**

| 场景 | 系统行为 |
| --- | --- |
| 普通任务提交 | 打卡、文本或链接提交后直接进入已完成状态；教师可查看，不以教师审批为前提 |
| 主观练习 | 无可靠评分规则时进入 `pending_review`，显示待反馈，不更新 BKT |

**画像事件来源：**

- 学生端：诊断、打卡、资源阅读、教师任务提交、客观评分和 BKT 更新。
- 教师端：任务发布/撤回、班级成员变化、成绩复核和资源发布。
- 画像刷新后，学生查看本人版本，教师查看本班班级画像和授权学生投影。

**联合预算：**

- 所有 AI 目标和教师任务共用学生日/周预算。
- 教师任务超过负荷时只生成重规划建议。
- 学生接受新路径前，原路径保持不变。

**版式：** 上半部分保留平台任务流程，下半部分重点画“事件 -> 水位 -> 画像快照 -> 学生/教师查看”的刷新闭环；右侧标出画像触发重规划的连接点。

**建议时长：** 约 100 秒。

#### 8. 第 7 页：B 的技术实现

**页面标题：** B 的技术核心是权限、事件水位、确定性画像与事务统计

| 技术层 | 具体技术 | 解决的问题 |
| --- | --- | --- |
| 前端 | React、TypeScript、React Router、TanStack Query | 角色页面、任务状态和进度查询 |
| 认证 | 用户名密码、Argon2 或 bcrypt、HttpOnly 会话 Cookie | 登录、会话恢复和账号停用 |
| 权限 | 服务端 RBAC、班级归属、学生分配归属、CSRF/同源策略 | 防止跨班、越权和伪造请求 |
| 平台业务 | FastAPI、SQLite 短事务、版本控制、幂等键 | 班级、任务、提交和状态更新 |
| 反馈 | 确定性评分、版本化 rubric、待复核状态 | 客观题即时反馈，主观题不伪造评分 |
| BKT | Python 概率计算、证据唯一键、掌握度快照 | 掌握度更新和评分更正重放 |
| 学生画像 | Student Profile Service、SQL/Python 聚合、规则版本、快照版本 | 汇总本人行为、掌握、证据和风险 |
| 班级画像 | Class Profile Service、本班授权投影、统计窗口、覆盖率 | 汇总班级参与度、任务、时长、薄弱点和风险 |
| 画像刷新 | Profile Refresh Service、领域事件、事件水位、`stale` 标记 | 识别过期、幂等刷新和保留历史 |
| 统计 | SQLite 聚合查询、索引、事件去重、短时缓存 | 班级完成率、按时率、逾期和时长 |
| 审计 | 结构化审计日志、管理员/教师操作记录 | 登录失败、发布撤回和越权追踪 |

**关键实现边界：**

- 所有受保护接口先确认角色，再确认班级或任务归属。
- 重复提交返回原结果，不重复统计或更新 BKT。
- 未登录返回 401，错误角色或跨班访问返回 403。
- 画像数值由 SQL/Python 确定性计算，LLM 只能解释已有事实。
- 画像读取必须返回版本、生成时间、统计窗口、数据水位、完整度和过期状态。

**主要数据：**

- `UserRole`
- `Classroom`
- `TeacherTask`
- `TeacherTaskAssignment`
- `Evidence`
- `MasterySnapshot`
- `StudentProfileSnapshot`
- `ClassProfileSnapshot`
- `ProfileRefreshEvent`
- `ReplanEvent`
- `AuditEvent`

**版式：** 五层技术架构图：React -> FastAPI/RBAC -> 班级/任务服务 -> 画像/BKT服务 -> SQLite；下方展示三类画像记录和主要数据对象。

**建议时长：** 约 90 秒。

#### 9. 第 8 页：B 的项目亮点与验收证据

**页面标题：** B 的亮点是画像可复算、可过期、可授权但不越权

**项目设计亮点：**

| 亮点 | 常规做法 | 本项目做法 |
| --- | --- | --- |
| 教师任务与 AI 路径解耦 | 教师任务直接插入计划 | 任务独立建表，联合检查预算，只产生重规划建议 |
| 对象级隐私投影 | 登录后能查看全班完整数据 | 教师只看本班授权数据，学生只看本人数据 |
| 可重放的 BKT | 每次评分直接改掌握度 | 保存证据与参数版本，同一证据只应用一次，更正后重放 |
| 可复算画像 | 让 LLM 总结学生或班级情况 | 事件水位触发 SQL/Python 聚合，LLM 只解释已计算事实 |
| 快照与过期识别 | 页面实时拼接数据或长期使用缓存 | 版本化快照、统计窗口、完整度、`stale` 和刷新历史 |

**验收示例：**

1. 指定学生收到教师任务，其他学生不可见。
2. 同一任务重复提交不重复计入完成率或 BKT。
3. 教师跨班访问和学生查看他人任务返回 403。
4. 0.62 先验配合默认参数和错误作答后，掌握度约为 0.343，可触发补强建议。
5. 行刷新后班级完成率、逾期人数和实际学习时长与提交记录一致。
6. 诊断、阅读、任务提交或评分后，学生画像生成新版本；旧版本仍可查询。
7. 教师班级画像只聚合本班授权投影，不混入私人目标或其他班证据。
8. 数据水位变化但刷新失败时，旧快照标记 `stale`，不冒充最新结果。

**证据记录：**

`版本 -> 用户角色 -> 输入 -> 预期 -> 实际 -> 响应码/快照 -> 结论`

**版式：** 左侧五行亮点对照，右侧按“学生画像、班级画像、过期刷新、隐私”四组排布验收示例；底部只保留证据记录格式。若信息偏密，把第 8 条移到讲述备注，不在页面缩成小字。

**表述边界：** 使用“项目设计亮点”，不把权限、BKT 或统计设计宣传为行业首创。

**建议时长：** 约 90 秒。
